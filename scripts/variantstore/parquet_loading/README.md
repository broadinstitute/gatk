# Parquet-Based BigQuery Loading

## Overview

GVS previously ingested data into BigQuery row-by-row via the BigQuery Storage Write API, inside the `LoadData` task. This approach was replaced with a two-phase design:

1. **`LoadData`** writes variant and reference data to local Parquet files and copies them to a temporary GCS path.
2. A downstream set of WDL tasks (described below) loads those Parquet files into BigQuery in bulk, using BigQuery's free GCS-to-BQ load jobs rather than the metered Write API.

The loading system is idempotent and survives VM preemptions without duplicating data.

## WDL Tasks (`GvsImportGenomes.wdl`)

Five tasks coordinate loading, verification, and cleanup after the `LoadData` scatter completes:

| Task                            | Purpose                                                                                                                                                                                                                                                                                                                                                                              |
|---------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `DiscoverParquetFiles`          | Lists all Parquet files in GCS, filters out already-loaded `(table_name, sample_id)` pairs by querying BigQuery directly, and emits one FOFN per target table.                                                                                                                                                                                                                       |
| `LoadParquetFilesToBQ`          | Scattered across all tables; loads each FOFN into its BigQuery table in batches of up to 10,000 files per load job.                                                                                                                                                                                                                                                                  |
| `VerifyParquetLoading`          | Re-queries BigQuery after all loads complete, runs exact structural checks (`completeness`, `cardinality`, `cross_family`) to gate `all_loaded`, and compares each sample's Parquet footer row counts against its BigQuery row counts (plus the `vet` truncation screen) to produce the per-sample quarantine list. Fails the workflow if any expected data is missing or corrupted. |
| `QuarantineFlaggedParquetFiles` | Moves the Parquet of flagged samples into a `quarantine/` subdirectory, renamed so it survives the bulk delete. Runs unconditionally and is a no-op when nothing was flagged.                                                                                                                                                                                                        |
| `DeleteParquetFiles`            | Deletes temporary GCS Parquet files only if `safe_to_delete_parquet` is true, and only after the quarantine step has succeeded.                                                                                                                                                                                                                                                      |

## Python Scripts (`scripts/variantstore/scripts/`)

All scripts are packaged into the variants Docker image at `/app/`.

| Script                        | Description                                                                                                                                                                                                                                                                                                                                                                                                                                              |
|-------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `parse_and_group_files.py`    | Discovers Parquet files under a GCS prefix, maps each file to its target BigQuery table and `sample_id`, queries `INFORMATION_SCHEMA.PARTITIONS` (and `sample_chromosome_ploidy` directly) to identify already-loaded pairs, and writes per-table FOFNs for the remaining files.                                                                                                                                                                         |
| `load_parquet_to_bq.py`       | Loads one FOFN into BigQuery. Generates a deterministic SHA-1 job ID per batch so that a retry VM after preemption re-uses the in-flight BigQuery job rather than re-submitting it. Retries quota and transient errors with exponential backoff (30 s → 60 s → 120 s, up to 3 retries).                                                                                                                                                                  |
| `verify_all_loaded.py`        | CLI coordinator that confirms every `(table_name, sample_id)` pair is loaded, executes structural verification via `verify_structural_checks.py`, logs detailed diagnostic summaries, writes `verification_results.json`, `missing_files.txt` and `quarantine_files.txt`, and exits non-zero if `all_loaded` is false.                                                                                                                                   |
| `verify_structural_checks.py` | Independent structural verification engine (VS-1989, VS-2032). Evaluates BigQuery partition and table counts for family completeness (no empty partitions), ploidy cardinality (`COUNT(*)` vs `COUNT(DISTINCT chromosome)` per sample), cross-family consistency across co-produced tables, a per-`(table, sample_id)` comparison of Parquet footer row counts against BigQuery row counts, and a cohort-relative truncation screen on `vet` row counts. |

## Verification and Deletion Gates (VS-1989)

Verification enforces a two-tier safety contract separating workflow success from data deletion authorization:

### 1. `all_loaded` (Workflow Gate)
Determines whether BigQuery ingestion succeeded. Governed exclusively by **exact** checks:
- **File Presence**: Every `(table_name, sample_id)` pair discovered in GCS must be confirmed present in BigQuery.
- **Family Completeness**: Every expected sample partition in superpartitioned tables (`vet_%`, `ref_ranges_%`) and every expected sample row in regular tables (`sample_chromosome_ploidy`, `vcf_header_lines_scratch`) must contain $> 0$ rows.
- **Ploidy Cardinality Consistency**: Detects duplicated loads exactly. Since `SamplePloidyCreator` emits at most one row per chromosome per sample, `COUNT(*) == COUNT(DISTINCT chromosome)` is verified per sample -- a doubled load repeats chromosomes and nothing legitimate does, so the comparison needs no reference count to compare against and holds for a single sample as readily as for a callset. Deliberately, no sample's row count is compared against any other's: those counts legitimately vary -- a chromosome gets a ploidy row only where a non-PAR reference block on it survived `drop_state` (`RefRangesCreator.apply`), so a sample's contig count depends on its data, not just its sex (every gVCF ingested for Foxtrot carries a chrY row, female participants included), chrM is recorded or not, and exome and BGE cover fewer contigs -- which is why the earlier modal ceiling and contig floor were dropped -- the ceiling only ever fired where the exact comparison already had, and the floor read a legitimately smaller contig set as a partial load. The gap that leaves is ploidy rows lost for *some* of a sample's chromosomes with no repeats, which no row count can distinguish from a legitimate karyotype; loss of the whole sample is still caught, by Family Completeness. Two further limits, since it is easy to over-read: it covers the ploidy table's own rows and is **not** a `ref_ranges` duplication detector -- a `ref_ranges` partition loaded twice is caught by the footer row count comparison below (VS-2032), not here. And where a sample's ploidy rows came from a later backfill rather than from ingest, the check is satisfied by construction and says nothing about how the data families loaded (`PLOIDY_BACKFILL_CAVEAT`).
- **Cross-Family Consistency**: A sample present in any co-produced family (`vet`, `ref_ranges`, `sample_chromosome_ploidy`, and conditionally `vcf_header_lines_scratch` when loaded alongside data) must be present in all configured co-produced families.

If any exact check fails, `all_loaded` is `false`, and `VerifyParquetLoading` exits non-zero, immediately aborting the workflow.

### 2. The per-sample quarantine: the footer row count comparison and the truncation screen
Two findings hold back *that sample's* Parquet rather than blocking deletion for the callset. Neither affects `all_loaded`. They differ in kind, and therefore in what an operator can do about them.

**The footer row count comparison (VS-2032) is exact and is not waivable.** For each `(table, sample_id)`, it sums the `num_rows` the sample's source Parquet footers declare and compares that against the rows BigQuery holds, across `vet`, `ref_ranges` and `sample_chromosome_ploidy` alike. Disagreement in either direction is a fact, not a ratio: more rows in BigQuery is a duplicated load, fewer is a lost one. There is no threshold to tune and nothing to waive, so a flagged sample's Parquet is always quarantined, and gate 4 below aborts on it by default.
- The footer counts come from a BigQuery external table over `<parquet_output_gcs_dir>/<family>/*.parquet`, one query per family since the families have different schemas. `SELECT _FILE_NAME, COUNT(*) ... GROUP BY _FILE_NAME` is answered from footer metadata, so it bills 0 bytes. Scoping the URI to the family prefix is also what excludes `quarantine/` and any sibling callset under a different submission.
- Only files in the discovery listing are counted, so a file written under the output directory after discovery cannot inflate a sample's sum; such files are reported as `unlisted_files` and otherwise ignored. A *listed* file the query did not return cannot be counted, so its sample cannot be cleared either: it is reported under `unread` and flagged alongside the mismatches. The query cannot tell an unreadable file from a valid one with zero rows, so `unread` covers both.
- Ingest writes exactly one Parquet file per family per sample, so a pair with more than one listed file is flagged under `multiple_files` whatever the counts say. Summing alone would miss it: a sample loaded once from each of two files reads $2N$ against $2N$. Re-running against the same output directory at a different scatter width produces exactly this, because the file name carries the sample's position in its shard (`input_vcf_<i>`).
- A family with no expected samples is not queried at all. A BigQuery wildcard that matches no files is an error rather than an empty result, so a headers-only pass — whose output directory holds no `vet/` — would otherwise fail the query outright.
- **Scope limit: this is exact with respect to *loading*, not to *generation*.** It compares the Parquet against BigQuery, and both sides are downstream of whatever `CreateVariantIngestFiles` wrote. A Parquet file that was itself generated with twice a sample's rows presents a footer of $2N$ against a partition of $2N$, which this check reads as agreement. Catching that needs a count taken from the input gVCF, which is out of scope here. The `vet` truncation screen below is the only detector for the analogous low-side case.

**The `vet` truncation screen is a heuristic, and is the only waivable finding.** It flags `vet` row counts below a floor (`parquet_vet_truncation_threshold`, default $1/1.6 = 0.625\times$ the cohort median), catching the one truncation source the footer comparison misses: a Parquet file generated upstream with far fewer rows than its peers, whose footer and BigQuery counts agree with each other.
- The threshold is provisional. It mirrors the $1.6\times$ ceiling of the duplication screen that VS-2032 retired — the Foxtrot pass measured that high side only, flagging 2 `vet` samples out of 540,545, and nothing has been measured below the median. A variant-count distribution has no reason to be symmetric in ratio space — its upper tail is bounded by biology, while its lower tail absorbs low-coverage samples, smaller callable fractions, and more aggressive GQ dropping — so the floor is an assumption of symmetry rather than a measurement. Switch it off with `parquet_vet_truncation_threshold = 0` (`--vet-truncation-threshold 0`); a disabled screen is logged and reported as disabled rather than as clean. This is why gate 4 below does not abort on it.
- It applies to `vet` only. `ref_ranges` row counts vary by orders of magnitude between legitimate samples, so a cohort-relative floor is meaningless there — which is exactly the gap the footer comparison now closes exactly.
- Singletons ($N=1$) are flagged conservatively, since no cohort consensus baseline exists. The baseline is drawn from the run's own samples, so this is a property of the batch and not of the dataset: a single-sample ingest into a 500k-sample callset has no cohort as far as the screen is concerned. See *Small incremental top-ups into an existing callset* below.
- If a flagged row count is verified as legitimate (e.g. a low-coverage sample or an expected singleton), the screen can be waived with `allow_flagged_vet_loads = true` (`--allow-flagged-vet-loads`), in which case its flagged Parquet is deleted with the rest. That flag does **not** waive the footer comparison; to finish a run the footer comparison flagged, turn off gate 4 instead, which keeps the evidence.

Either way, `QuarantineFlaggedParquetFiles` moves every Parquet file belonging to a flagged sample — across **all** families, not just the flagging one, since a sample is only re-ingestable from a complete set of its files — into a `quarantine/` subdirectory of the Parquet output directory, appending `.quarantined` to each name. The rest of the callset's Parquet is then deleted as usual.

Two independent properties keep quarantined files alive, and both matter:
- **The rename.** `DeleteParquetFiles`' default strategy globs `*.parquet` across the whole output directory, so a quarantined object survives it only because its name no longer ends in `.parquet`. The task asserts that the configured suffix does not itself end in `.parquet`.
- **The location.** `DeleteParquetFiles`' alternate strategy deletes the four table directories, and the bucket lifecycle rule `ConfigureParquetLifecycle` installs matches those same four prefixes with a 14-day `Delete` action. `quarantine/` is in neither list, so quarantined files are exempt from both. **Nothing removes them**: clean the directory up by hand once the samples have been reviewed. A `README.txt` written alongside them explains how to restore one.

**Quarantining does not touch BigQuery.** `QuarantineFlaggedParquetFiles` runs `gcloud storage mv` and nothing else; the verification scripts only ever read from BigQuery. A flagged sample is loaded exactly like any other — `all_loaded` is true and `SetIsLoadedColumn` sets its `sample_info.is_loaded` — so a sample flagged by the footer comparison keeps its suspect rows in BigQuery. The quarantine preserves the evidence needed to re-ingest; it does not roll the load back.

That makes re-ingesting a quarantined sample a **two-step** operation, and restoring the Parquet alone is a silent no-op: `parse_and_group_files.py` treats a `(table_name, sample_id)` pair as already loaded whenever the rows are there — for `vet_%` and `ref_ranges_%` whenever the partition reports `total_logical_bytes > 0`, which a duplicated partition certainly does, and for the unpartitioned tables whenever the `sample_id` appears in them at all — so the restored file is skipped and the run comes back green having done nothing. Delete the sample's rows from BigQuery first, across every family the sample was quarantined under, then restore and re-run. `DELETE ... WHERE sample_id = <sample_id>` is the form that works everywhere. For `vet_%` and `ref_ranges_%` only, `bq rm -f -t 'project:dataset.vet_00N$<sample_id>'` is equivalent and cheaper, the partition id being the `sample_id` for those step-1 range-partitioned tables; it does not apply to `sample_chromosome_ploidy` or `vcf_header_lines_scratch`, which are created unpartitioned (`GvsAssignIds.wdl`) and reject the partition decorator outright. Row presence is the loader's test for those two, so the `DELETE` is what clears it. The generated `README.txt` spells this out in place.

Quarantining per sample rather than withholding the run's delete is what keeps a per-sample finding out of a callset-wide decision. On Foxtrot the calibration pass flagged 2 `vet` samples out of 540,545; under a run-wide gate that would have retained every sample's Parquet — and only until the 14-day lifecycle rule deleted it anyway, silently, in a green run.

### 3. `safe_to_delete_parquet` (Deletion Gate)
The gate governing whether `DeleteParquetFiles` runs at all:
- Requires `all_loaded == true`.
- Requires every flagged sample to have at least one resolvable Parquet path, so the quarantine step has something to move. A flagged sample with no such path blocks deletion, because running it would destroy exactly the files the checks asked to keep.
- A flag alone does **not** block it; see the quarantine above.
- `DeleteParquetFiles` additionally consumes `QuarantineFlaggedParquetFiles.done`, so a failed quarantine takes the delete down with it. That ordering is structural rather than a boolean, because a failed quarantine followed by a bulk delete is the one unsafe sequence.

### 4. `parquet_fail_on_quarantine` (Notification Gate)
Quarantining makes a flagged run *succeed*, which leaves the opposite problem: a run that needs a human look is green, and the only trace is a workflow output nobody reads. `parquet_fail_on_quarantine` (default `true`, forwarded from `GvsJointVariantCalling` and `GvsBulkIngestGenomes`) closes that gap by aborting such a run via `Utils.TerminateWorkflow`.
- The abort is **purely a notification**. It runs after `QuarantineFlaggedParquetFiles`, so the samples are loaded and their Parquet is already safe: nothing is destroyed and nothing is rolled back. Re-running with `parquet_fail_on_quarantine = false` (or `parquet_allow_flagged_vet_loads = true`, once the flag has been reviewed and dismissed) finishes from a fully loaded dataset.
- It is conditioned on `QuarantineFlaggedParquetFiles.quarantined_files`, not on the equivalent `VerifyParquetLoading` count. The data dependency is what places the abort after the move; terminating off the verification output would let Cromwell kill the workflow while the flagged files were still under the prefixes the 14-day lifecycle rule matches, neither quarantined nor deleted.
- `DeleteParquetFiles` depends on the same task, so it and the abort are siblings and Cromwell may start the delete first. That race is benign: the delete skips quarantined files by both suffix and location, and deleting the unflagged samples' Parquet is wanted either way.
- **Only the footer row count comparison aborts.** A truncation-only flag still quarantines and still reports, but that threshold is uncalibrated, and an uncalibrated heuristic should not be able to fail a completed 500k-sample ingest. `VerifyParquetLoading` reports the footer subset separately (`quarantine_row_count_mismatch_sample_count`) for exactly this reason.
- **`parquet_allow_flagged_vet_loads = true` no longer supersedes this gate.** It did under VS-1989, when waiving the screens emptied the quarantine work list and left an abort conditioned on `quarantined_files` with nothing to fire on. VS-2032 narrowed the waiver to the truncation screen, so a footer row count mismatch still quarantines and still aborts however that input is set. To finish a run the footer comparison flagged, turn this gate off. That is also the better choice for a truncation flag: `parquet_fail_on_quarantine = false` keeps the flagged sample's Parquet under `quarantine/` with its restore `README.txt`, while `parquet_allow_flagged_vet_loads = true` lets that Parquet be deleted along with the rest and writes no README, leaving only the `parquet_vet_truncation_flagged` boolean as a trace. So reach for the waiver only once the flag has been reviewed and dismissed.

### Small incremental top-ups into an existing callset

The truncation screen draws its baseline from the samples loaded by the current run, not from the dataset around them — `assess_truncation_screen` filters the partition rows down to the run's expected `sample_id` set before computing a median. That is the right cohort for an ordinary batch, but it degenerates when a run adds only a handful of samples to an already-populated callset, which is what a top-up into a dataset whose bulk arrived earlier looks like (whether that bulk came from Parquet or from the older BQ Storage Write API path). The footer row count comparison is unaffected: it compares each sample against its own Parquet, so it has no cohort to degenerate.

- $N=1$ has no cohort at all, so the sample is flagged unconditionally and its Parquet is quarantined. Under VS-1989 that also aborted the run, because the duplication screen flagged the singleton too; now that only the footer comparison aborts, a singleton top-up finishes green with a quarantine to review.
- $N=2$ takes its baseline from one of the two observed values, so two legitimately dissimilar samples flag each other.

Neither is a data problem. `all_loaded` is unaffected, the samples are loaded, and the flagged Parquet is quarantined rather than lost. For a deliberate small top-up, leave it at that and clean up the quarantine directory by hand, or set `parquet_allow_flagged_vet_loads = true` to waive the screen outright and let the flagged Parquet be deleted with the rest.

Widening the baseline to the whole callset is tracked in [VS-2027](https://broadworkbench.atlassian.net/browse/VS-2027). It would cost no additional BigQuery read — `get_partition_row_counts` is already unscoped and reads every `vet_%` partition's row count before the screen discards everything outside the run — but it needs a decision on how to treat mixed-assay datasets, so the run-scoped baseline is the current behavior by choice rather than by oversight.

### Observability on a successful run
When the abort is off, or when only the truncation screen fired, the run is green and the flags and quarantine counts are published as workflow outputs (`parquet_row_count_mismatch_flagged`, `parquet_vet_truncation_flagged`, `parquet_quarantined_samples`, `parquet_quarantined_row_count_mismatch_samples`, `parquet_quarantined_files`, `parquet_quarantine_files_list`), from `GvsImportGenomes` up through `GvsBulkIngestGenomes` and `GvsJointVariantCalling`. A non-zero `parquet_quarantined_samples` on a green run is the signal to go and look.

`GvsQuickstartVcfIntegration` asserts that count is zero whenever `parquet_fail_on_quarantine` is on. The quickstart callset is ordinary and is loaded exactly once, so a flag there is a regression in the checks rather than bad input data — and since a truncation-only flag does not abort inside `GvsImportGenomes`, the assertion is what keeps that case from passing CI silently. Turning `parquet_fail_on_quarantine` off suppresses this assertion too, so it means the same thing at both layers: a quarantine does not fail the run. That is what lets a deliberately forced quarantine — a raised truncation threshold on an ordinary cohort — exercise the whole path and still finish green.

### Diagnostic Persistence
On verification failure (`rc != 0`), `VerifyParquetLoading` copies `verification_results.json` to `verification_diagnostics_gcs_dir` (if specified) before exiting. This copy is gated on failure so successful retries cannot overwrite the durable failure diagnostics.

A green run that quarantined anything gets the same treatment, under distinct names (`verification_results.quarantine.json` and `quarantine_files.txt`). Without it the only record of why those files were set aside would be the Cromwell execution directory, which is exactly what gets cleaned up. The separate names preserve the invariant above: this path does re-run on a successful retry, so it must not be able to overwrite a preserved failure diagnostic.

## Key Design Points

**Idempotency** is based on what BigQuery actually contains, not a secondary tracking table. `parse_and_group_files.py` queries `INFORMATION_SCHEMA.PARTITIONS` for non-empty integer partitions in the `vet_%` and `ref_ranges_%` tables, and queries `sample_chromosome_ploidy` directly for distinct `sample_id` values. Files belonging to already-loaded pairs are silently skipped on every run.

**Preemption recovery** relies on deterministic BigQuery job IDs (a SHA-1 hash of the project, dataset, table name, and sorted batch file list). When a retry VM submits the same batch, BigQuery returns a `Conflict` exception; `load_parquet_to_bq.py` catches this and fetches the pre-existing job to wait on, so no data is written twice and no local state file is required.
